# Is BanditRS a drop-in replacement? The evidence

Generated by `scripts/parity_report.py`. Every number here comes from running both tools;
nothing is asserted that a command in this repository cannot reproduce.

## Summary

| Question | Answer |
|---|---|
| Same issues on real third-party code? | **24/24 packages identical** — 11,624 files, 3,640,954 lines, 73,577 issues |
| Same stdout, stderr **and exit code** across the CLI? | **85/88 invocations identical**, 3 documented divergence(s) |
| How much of the tool does that exercise? | **56/75 test ids** triggered by the corpus; the rest are covered by `examples/` (see §3) |
| How much faster? | **53.3×** over the whole corpus (286.0 s → 5.4 s) |

## 2. The command-line surface

`scripts/cli_matrix.py` runs 88 invocations through both tools and compares stdout, stderr and
the exit code. It covers the severity and confidence thresholds, test selection and skipping, profiles
and config files, all nine formatters, `--msg-template`, `-o`, context lines, aggregation, `-q`/`-v`/`-d`,
`--exit-zero`, `--ignore-nosec`, target discovery (recursive or not, excludes, globs, symlinks, missing
paths, empty directories, non-UTF-8 and unparsable files), `.bandit` handling, every usage error that
exits 2, baselines, and the `bandit-baseline` / `bandit-config-generator` binaries.

Result: **85/88 identical**.
 The 3 exception(s) are documented in `DEVIATIONS.md`:

- `config_bad` — DEVIATIONS.md #19: PyYAML's parse-error wording for an invalid config
- `debug` — DEVIATIONS.md #18: -d dumps the Python Context dict, ast node reprs included
- `fmt_yaml` — DEVIATIONS.md #10: PyYAML anchors/aliases for a shared line_range list

`cargo test --test cli_matrix` replays the recorded reference surface with no Python installed, so a
regression in any of these is caught by the ordinary test run.

## 4. The parser target, measured

BanditRS parses with `ruff_python_parser`, whose target version is set by
`BANDITRS_PYTHON_COMPAT`; the reference parses with the host interpreter's `ast`. This is worth
being precise about, because it is easy to mistake for a parity gap.

**With the target aligned to the reference (`BANDITRS_PYTHON_COMPAT=3.11`), there is no gap at
all** — including on packages that require Python 3.12. The `frontier` tier is made of exactly
those packages, and with the target aligned both tools produce identical reports, `errors[]`
included: BanditRS refuses the same files, for the same reason.

The numbers below are the *other* regime — BanditRS left on its default (latest) target against a
3.11 reference — which is what quantifies the difference (DEVIATIONS.md #16):

| package | files | errors (python) | errors (rust) | issues (python) | issues (rust) |
|---|---:|---:|---:|---:|---:|
| `Django 6.1.1` | 2,907 | 6 | 1 | 1,236 | 1,279 |
| `ansible-core 2.21.4` | 1,802 | 28 | 0 | 3,675 | 3,705 |

Where the reference records a syntax error and analyses nothing, BanditRS analyses the file, so it
reports *more*. The remaining difference is the 3.12 f-string constant positions (DEVIATIONS.md
#7), which move issues found inside an f-string. Comparing against a reference means matching its
interpreter version; every harness in this repository sets the target accordingly, and every
package in the parity tiers is additionally pinned to a release CPython 3.11 parses in full
(`scripts/corpus.py verify --parse`).

## Reproducing

```
cargo build --release
scripts/corpus.py fetch  --tier standard      # pinned by sha256, ~200 MB
scripts/corpus.py verify --parse              # precondition: all of it parses under 3.11
scripts/diff_corpus.py   --tier standard --json target/parity/standard.json
scripts/cli_matrix.py    diff
scripts/parity_report.py --parity target/parity/standard.json
```
